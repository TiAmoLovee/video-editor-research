# ClipForge 每周工作记录

## 第二周：媒体流水线骨架与最小闭环

### 本周目标

完成“上传视频 → 后台处理 → 进度显示 → 下载切片”的最小流程。视频归一化为 CFR 30 fps / H.264 / AAC，按每段最多 30 秒切片。

当前已完成本地媒体处理模块、FastAPI 服务与 Celery/Redis 加法任务联调。视频处理尚未接入后台任务接口，前端页面尚未实现，MVP-0 整体闭环仍在开发中。

### 本周完成

#### 1. 开发环境与 Git 工作流程

- 使用 Git 命令克隆仓库，核对分支、远程地址和提交历史。
- 创建第二周开发分支 `week2/mvp0`，练习本地修改、检查差异、暂存、提交和远程同步。
- 安装并验证 Python 3.11.9，创建项目独立环境 `.venv`。
- 配置 `.gitignore`，忽略虚拟环境和 Python 缓存文件。

#### 2. 视频信息读取与统一格式

- 实现 `probe.py`：调用 FFprobe，将 JSON 输出解析并整理为项目统一的视频信息结构。
- 新增 `schemas/media_meta.schema.json`，定义字段类型和未知值的表示方式。
- 使用 `Sucai1.mp4` 验证读取结果：时长约 41.27 秒，分辨率 960×600，视频编码 HEVC，平均帧率 30 fps，音频编码 AAC、44.1 kHz、单声道。
- 保存元数据样本 `docs/samples/media_meta.json`。

#### 3. 视频归一化转码

- 实现 `normalize.py`，复用视频信息读取功能，将素材转为 H.264 / AAC、恒定 30 fps 的 MP4。
- 实现原素材保护、已有输出拒绝覆盖、转码超时及失败处理。
- 真实素材转码后，基本参数检查和人工播放检查通过。
- 助手另行检查 Python 转码产物的 1,238 帧时间戳，相邻帧间隔均为 1/30 秒。
- 补充 `docs/NORMALIZATION.md`，记录运行方法、验证结果和当前限制。

#### 4. 固定时长自动切片

- 实现 `split.py`，按每段 900 帧规划切片，在 30 fps 下对应每段最多 30 秒。
- 根据切片清单执行转码，保存 `clip_plan.json`，记录片段边界和帧数。
- 真实归一化素材自动生成两段，经程序检查分别为 900 帧和 338 帧。
- 补充 `docs/SPLITTING.md`，记录运行方法与验证范围。

#### 5. 自动化验证

- 媒体模块 22 项单元测试通过：7 项元数据转换测试、7 项转码约束与文件保护测试、8 项切片边界与目录保护测试。
- 新增 7 项接口逻辑测试，覆盖提交响应、队列异常、状态读取、输入约束和接口文档；与媒体测试合计 29 项，在交付验证环境中全部通过。接口单元测试使用队列替身。
- 运行 `tests/integration_split.py`，真实调用 FFmpeg，以下媒体集成实验通过：
  - 5 分钟、9,000 帧的合成素材生成 10 个切片，每段 900 帧。
  - 901 帧的合成素材生成 900 帧与 1 帧的两段，保留真实尾帧。
  - 编码器缺失时正确返回失败，不遗留最终结果目录或临时目录。

以上是本地媒体模块验证，尚不等同于通过后台接口提交视频并获取结果的系统集成测试。
#### 6. 后端接口骨架

- 新增 api.py，使用 FastAPI 定义服务，通过 Uvicorn 在本地运行。
- 实现 GET /health，浏览器访问后返回服务状态。
- 验证 /docs 自动接口文档能够正常打开。
- 生成 requirements.txt，记录当前环境的依赖版本，pip check 检查通过。
- 健康检查保留；当前另有后台加法任务提交和状态查询接口，视频上传、视频任务、百分比进度和下载接口尚未实现。

#### 7. Docker 后台队列与 HTTP 联调

- 使用 Docker Compose 部署 Redis、Celery worker 和 FastAPI；worker 在 Linux 容器中运行。
- 命令行队列实验通过：提交 2 + 3，后台执行后取得结果 5。
- 实现 `POST /demo/tasks`，返回 HTTP 202、任务编号与查询地址；请求不等待计算结束。
- 实现 `GET /demo/tasks/{task_id}`，读取任务状态快照与结果。
- 2026-09-21 在本机运行 `tests/integration_queue_api.py --base-url http://127.0.0.1:8200`，实际观察到 PENDING → STARTED → SUCCESS，结果为 5；非法参数、非法编号及未知编号语义检查通过，脚本输出 PASS。
- ClipForge 使用宿主机 8200 端口，映射容器内 8000；Redis 不开放宿主机端口。
- 记录 PENDING 可能表示未执行、未知编号或结果过期，不能代替任务数据库的存在性判断。

### 技术障碍与当前假设

- Python、FFprobe 和 FFmpeg 已能在 Windows 本机运行；Redis、Celery worker 与 FastAPI 容器已完成加法任务联调。
- 接入视频任务前，需要为 worker 容器安装 FFmpeg，并让 API 与 worker 访问同一份上传文件和处理结果；Windows 的 `D:\Shotcut` 路径不能直接作为 Linux 容器内的程序路径。
- 当前使用 Shotcut 自带的 FFmpeg 8.1 系列，与任务书列出的 6.1 / 7.x 不同。已记录本机版本，尚未验证其他版本的兼容性。

### 失败的尝试

- **Git 直连推送失败**：出现连接重置或无法连接 GitHub 的错误。显式使用本地代理，并完成 Git 身份认证后，推送成功。
- **安装后终端找不到 Python**：`python` 命令仍指向 Windows 商店入口。确认实际安装成功后，改用 `py -3.11` 和项目虚拟环境中的解释器，运行成功。
- **工作记录未进入暂存区**：文件保存时间晚于此前的 `git add`，导致提交预览中缺少该文件。保存后重新暂存，修改正常进入待提交内容。

- **Docker 镜像拉取超时**：Docker Hub 认证和下载曾超时，明确配置 Docker Desktop 的本地 HTTP 代理后成功拉取基础镜像并构建服务。
- **API 端口冲突**：宿主机 8000 已被 Docker 服务占用；将 ClipForge 映射改为 `127.0.0.1:8200:8000`，启动及 HTTP 集成测试通过。
- **Compose 配置缺少服务**：一次检查发现配置仅保留 Redis，补齐 worker 与 api 后恢复启动。
